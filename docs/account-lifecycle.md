# 财务账户生命周期业务文档（Account Lifecycle）

> 覆盖：账户的创建/编辑、批量保存（UPSERT）、停用（含余额处置）、合并、彻底删除、重新启用，
> 以及背后的账务规则、状态机、守卫与错误码、客户端交互设计思想。
> 本文与当前前后端实现严格对齐；如代码演化，请同步更新本文。

---

## 1. 模块定位与核心设计原则

账户在系统中扮演两个角色：

1. **余额载体**：每个账户有一个 `initialBalance`（期初）与 `currentBalance`（当前余额）；
   `currentBalance` 由账本推导：`currentBalance = initialBalance + Σ 已清算交易的符号效果`。
2. **交易维度**：每一笔交易都挂在某个账户上（`source_account_id` / `target_account_id`），
   是收支报表、净资产统计、AI 分析的最小维度。

由此导出三条**不可动摇**的原则：

| 原则 | 含义 | 直接推论 |
|---|---|---|
| ① 历史不可销毁 | 交易流水是用户账目的原始凭证，任何操作都不得使其丢失或静默改写 | 删除只允许“零历史”账户；有历史账户走合并/停用 |
| ② 账本必须自洽 | 任意时刻 `currentBalance` 都能由流水重算出来，不依赖某次“拍脑袋改数字” | 余额处置必须生成真实的交易流水，而不是直接改余额字段 |
| ③ 生命周期显式化 | 停用/删除是不可逆或半可逆的重大决定，必须有专用入口与明确语义，不能藏在普通编辑里 | 普通编辑不能把账户置为 CLOSED；停用只能走停用端点 |

一句话概括：
**历史永存（可迁移、不销毁）；账户身份可复用（停用/启用）；物理删除只给从未产生过历史的空账户。**

## 2. 状态机与操作矩阵

账户只有两种状态：

```
        PATCH status=ACTIVE (重新启用)
      ┌──────────────────────────────┐
      ▼                              │
   ┌───────┐   CLOSE（停用端点）    ┌────────┐
   │ ACTIVE │ ───────────────────▶ │ CLOSED │
   └───────┘                       └────────┘
        ▲                               │
        │        DELETE（仅空账户）      │（有历史：只能先合并）
        └───────────────────────────────┘
```

| 操作 | ACTIVE | CLOSED | 说明 |
|---|---|---|---|
| 编辑名称/类型/性质/是否计入净值 | ✅ | ✅ | 普通编辑 |
| 编辑期初/当前余额 | ✅ | ✅（不建议） | PATCH 有余额平移语义 |
| 停用（CLOSE） | ✅ | ❌（已停用→ 409，code 3301） | 只有活跃账户可以被停用 |
| 合并到其他账户（MERGE） | ✅（源/目标） | ✅ 可作**源**；❌ 作目标（3308） | 合并是迁移校正路径，源账户可任意状态 |
| 彻底删除（DELETE） | ✅ 仅空账户 | ✅ 仅空账户 | 与状态无关，只看“是否有历史+余额是否为零” |
| 重新启用（REOPEN） | ❌ 无意义 | ✅ | 显式入口，普通编辑不会静默复活 |

**关键澄清（FAQ 详述）**：*重新启用 ≠ 可删除*。删除的许可不取决于状态，
而取决于“这个账户是否承载了历史”。停用账户保留全部历史，重新启用后历史依旧在，
所以依然不能直接删除——要移除账户本身只能“合并到其他账户”。

## 3. 六种核心操作详解

### 3.1 创建 / 批量保存（UPSERT）

- `POST /user/financial-accounts`（单个创建）
- `POST /user/financial-accounts`（批量保存，客户端编辑页保存整组）

批量保存语义：
- 按 `id` 匹配：已存在 → 就地更新（**identity 保持**）；无 `id` 或缺 id → 新建；
- **余额绝不被重置**：即使客户端回传了旧余额，服务端也以库内为准，交易驱动产生的余额不会被“回写”抹掉；
- 不存在的账户不会被批量删除（禁止隐式清理）；
- `status=CLOSED` 的账户在批量保存中**保持 CLOSED**——普通编辑不会把停用账户静默改回活跃。

### 3.2 编辑（PATCH，`PATCH /user/financial-accounts/{id}`）

- 字段：名称、性质、类型、币种、期初余额、当前余额、是否计入净值、状态；
- **余额语义（账本友好）**：
  - 同时给 `initialBalance` + `currentBalance` → 两者权威覆盖；
  - 只给 `initialBalance` → 按差值**平移** `currentBalance`（累计交易效果保留，而不是被清零）；
  - 只给 `currentBalance` → 直接覆盖（显式余额修正）；
- **状态守卫**：`status=CLOSED` 一律拒绝（3301 语义），必须走停用端点；
  反过来 `status=ACTIVE` 允许 → 这就是“重新启用”的服务端实现。

### 3.3 停用（CLOSE，`POST /user/financial-accounts/{id}/close`）

**业务意义**：模拟现实世界“注销/关闭一个账户”，同时完整保留它的历史流水。
停用后账户不再出现在新建交易的可选账户里、不再计入净资产汇总，但历史报表完整。

**前置守卫**：
- 账户必须存在（404）且当前是 ACTIVE（已停用 → 409，code 3301）；
- **禁用场景**：账户仍被**周期规则**引用 → 拒绝（code 3304），
  提示先停用规则或把规则合并到其他账户（周期规则会持续向已停用账户生成未来交易，必须先解绑）。
- 普通交易历史**不**阻止停用——停用正是为保留历史而生的。

**余额处置（`disposal`）**：停用时余额若非零，必须三选一（详见 §4）。

**收尾**：`status=CLOSED`；处置流水产生后，用账本重算刷新快照余额（与流水严格一致）；
返回 `{account_id, status, disposal, transaction_id, final_balance}`。

### 3.4 合并（MERGE，`POST /user/financial-accounts/{id}/merge`）

**业务意义**：账户是“错误/重复/需要迁移”时的**校正与迁移路径**——把源账户的历史整体搬到目标账户，
然后源账户从系统中消失（物理删除，但历史以“目标账户名下的交易”形式继续存在）。

行为：
1. 校验：不能合并到自身（3308）；币种必须相同（3309）；性质必须相同——资产只能并资产、负债只能并负债（3310）；目标必须是活跃账户（3311）；
2. 把源账户的全部交易/周期规则的 `source`/`target` 重指到目标账户；
3. 目标账户余额按账本重算（流水变了，余额跟着变）；
4. 删除源账户（它已不再承载任何历史）。

**合并是唯一能让“有历史的账户身份”从系统中消失的路径。**

### 3.5 彻底删除（DELETE，`DELETE /user/financial-accounts/{id}`）

**业务意义**：只允许物理删除“从未产生历史 + 余额为零”的账户。这种账户不携带任何原始凭证，
删掉不会丢任何东西（例如误建的空账户、创建后从未用过的账户）。

守卫（按顺序）：
1. **引用守卫**：存在任何交易或周期规则引用 → 409：
   - 账户已停用（CLOSED）且有引用 → **code 3312**：专门提示“已停用并保留全部历史记录；如需彻底移除，请先合并到其他账户”；
   - 账户活跃且有引用 → **code 3302**：提示“先合并或先停用”；
2. **余额守卫**：余额非零 → 409（code 3303）：提示“先合并，或在停用时处置余额”；
3. 通过 → 物理删除 + 提交。

**删除是纯“清理”入口，不具备“迁移”能力；需要迁移请用合并。**

### 3.6 重新启用（REOPEN）

- 客户端：编辑页管理菜单中对 CLOSED 账户显示「重新启用账户」入口（确认弹窗 → PATCH `status=ACTIVE`）；
- 服务端：即普通 PATCH 置 `ACTIVE`（PATCH 只拒绝置 CLOSED，允许 CLOSED→ACTIVE）；
- 效果：账户回到活跃集合，重新计入净资产、可再次选作交易账户；**余额即当前快照**（
  保留冻结 = 停用时的余额；转出/核销 = 归零后的余额）；全部历史流水原样保留。

## 4. 余额处置：业务含义与账务细节（重要）

停用时若余额 ≠ 0，三种处置各有明确业务含义。**无论哪种，余额的归零/转移都通过真实交易流水完成**，
绝不直接改余额字段，保证账本自洽。

| 处置 | 含义（一句话） | 生成的流水 | 对净资产影响 | 适用场景举例 |
|---|---|---|---|---|
| `keep` 保留为冻结快照 | “余额我认，但不再变动” | **不生成**流水，余额定格 | 余额继续计入净资产 | 数字钱包关停、账户归档，余额本就是最终值 |
| `transfer` 转出到另一账户 | “余额我**还要**，搬走” | 生成 **TRANSFER** 流水 | 不变（资产平移/债务转移） | 注销银行卡前把余额转出 |
| `writeoff` 记为支出核销 | “余额我**不要了**，承认它没了” | 生成 **EXPENSE** 或 **INCOME** 流水 | 净资产相应减少/增加（诚实记账） | 预付卡剩零钱放弃、坏账核销、债务豁免 |

### 4.1 符号规则（与账本约定严格一致）

账本约定：
- `EXPENSE` → 扣减 **source** 账户；
- `INCOME`  → 增加 **target** 账户（挂 source 的 income 无效）；
- `TRANSFER`→ source −、target +；
- 负债账户余额用**负数**表达“欠款”。

按余额**符号**（而非账户性质）决定方向，任何账户都能精确归零：

| 场景 | 处置 | 流水形态 |
|---|---|---|
| 资产正余额（+120） | writeoff | `EXPENSE`，source=停用账户 → 120−120=0（视同花掉/损失/坏账） |
| 负债负余额（欠 3000） | writeoff | `INCOME`，target=停用账户 → −3000+3000=0（视同债务豁免） |
| 资产正余额（+120） | transfer | `TRANSFER`，source=停用账户 → 目标 +120，停用账户归零 |
| 负债负余额（欠 3000） | transfer | `TRANSFER`，**source=目标账户，target=停用账户** → 停用账户 +3000 归零，债务落到目标（债务转移） |
| 任意余额为零 | 任意 | 处置被自动降级为 `keep`（无余额可处置） |

> 历史教训：早期实现按“性质”而非“符号”选方向，导致负债账户核销时余额越核越负、
> 债务转移方向颠倒。已修复并补回归测试（`test_close_liability_*`）。

### 4.2 流水的“来源”与语言

- 处置流水：分类 `OTHERS`，来源列固定 `SYSTEM`（可追溯为系统生成，区别于用户手记/AI）；
- `raw_input`（流水备注）按客户端 `Accept-Language` **创建时快照**本地化：
  `停用时余额转出/核销`、`停用時餘額轉出/核銷`、`口座停止時の残高振替/処理`、`계좌 정지 시 잔액 이체/정리`、英文兜底；
- 备注与用户手输备注同语义（创建时快照），切换语言后历史流水不随语言变化。

## 5. 守卫与错误码速查表（AccountErrorCode 3300–3312）

| 码 | 常量 | 场景 | 客户端提示（本地化） |
|---|---|---|---|
| 3300 | `accountNotFound` | 目标/账户不存在 | 账户不存在 |
| 3301 | `accountAlreadyClosed` | 重复停用 | 该账户已停用 |
| 3302 | `accountDeleteReferenced` | 活跃账户有引用直接删 | 仍有交易或周期规则，先合并或停用 |
| 3303 | `accountDeleteBalanceNotZero` | 活跃账户余额非零直接删 | 仍有余额，先合并或停用时处置 |
| 3304 | `accountCloseRecurringActive` | 停用时仍有周期规则 | 先停用/迁移规则 |
| 3305 | `accountCloseTargetRequired` | 转出处置未指定目标 | 转出余额需要目标账户 |
| 3306 | `accountCloseTargetClosed` | 转出目标是已停用账户 | 目标已停用，换一个 |
| 3307 | `accountCloseTargetCurrencyMismatch` | 转出目标币种不同 | 转入账户需要同币种 |
| 3308 | `accountMergeSelf` | 合并到自身 | 不能合并到自身 |
| 3309 | `accountMergeCurrencyMismatch` | 合并币种不同 | 币种不同无法合并 |
| 3310 | `accountMergeNatureMismatch` | 资产并负债/负债并资产 | 资产与负债无法互并 |
| 3311 | `accountMergeClosedTarget` | 目标是已停用账户 | 先重新启用或换目标 |
| 3312 | `accountDeleteClosedHasHistory` | 停用账户有历史直接删 | 已停用并保留全部历史，请先合并 |

客户端三层映射：`error_codes.dart`（int）→ `error_translator.dart` → `errorMapping.account.*`（5 语言）。
所有拦截提示均为本地化文案，不再透出服务端英文。

## 6. UI 交互设计思想

### 6.1 一致性原则：一切管理菜单/选择器复用系统组件

- 账户管理菜单（合并/停用/删除/重新启用）与全局所有“三点菜单”一致，使用 `ActionBottomSheet`：
  拖拽手柄 + 标题 + 分隔线 + 图标项 + **副标题说明**；点击项由组件自行 pop（带 `result`），调用方绝不二次 pop（避免 go_router 双重弹栈崩溃）；
- 余额处置选择（保留/转出/核销）使用**同款** `ActionBottomSheet`，每项附一句话解释其真实账务含义；
- 合并目标 / 转出目标选择复用系统 `AccountSelectionSheet`（交易表单同款：标题 + 取消 + 账户卡片列表），
  通过 `filter` 注入“同币种 + 活跃 +（合并时）同性质 + 非当前账户”，替用户把服务端会拒绝的选项提前过滤掉。

### 6.2 CLOSED 账户的视觉与入口

- **列表**：已停用账户**置灰（透明度 0.55）** + 名称旁「已停用/Closed」徽章，一眼可辨；
- **编辑页管理菜单**：CLOSED 账户显示「重新启用账户」作为主操作，不再显示「停用」（已停用无意义）；
- **删除入口保留**，但被服务端以专门文案引导（3312）：已停用账户要“消失”请走合并；
- 普通编辑保存**不会**静默复活已停用账户（UPSERT 保留 CLOSED）。

### 6.3 引导而非报错

- 每个拦截场景都给出**下一步动作**（先合并 / 先停用 / 换目标 / 重新启用），而不是干巴巴的“不允许”；
- 错误码细分到场景，文案本地化，便于跨端一致。

## 7. 常见误区问答（FAQ）

**Q1：停用账户可以重新启用，为什么删除还是提示“已停用并保留全部历史”？**
A：删除的许可与状态无关，只看“是否承载了历史”。停用的承诺就是保留历史——既然历史在，它永远不能直接删。
重新启用只是把账户从归档区放回活跃区（重新计入净值、可再选作交易账户），历史原封不动。
**要让这个账户身份消失：合并到其他账户**（历史迁到目标名下，源账户移除）。

**Q2：为什么停用时不让我直接把余额改成 0？**
A：直接改数字会让账本不自洽（流水总和 ≠ 余额），报表/对账会坏。必须用一笔真实的支出/收入/转账流水把余额冲平，
这样“余额去哪了”永远可追溯。

**Q3：删除 / 停用 / 合并，到底怎么选？**
```
账户承载过历史（有交易/规则）？
 ├─ 账户本身是错的/重复的 → 合并到正确账户（历史迁移，源消失）
 ├─ 账户是真实存在的，只是不用了 → 停用（余额三选一处置，历史保留，可重新启用）
 └─ 想彻底移除账户身份 → 只能先合并（删除不允许有历史）
账户从未承载历史且余额为零 → 删除（物理清理）
```

**Q4：负债账户（欠款）也能“转出/核销”？**
A：能。负债余额用负数表达欠款：转出 = 债务转移（债务落到目标账户）；核销 = 债务豁免（记为收入入账，欠款归零）。
方向由余额符号自动决定，用户无需记规则。

**Q5：停用/合并生成的流水备注为什么是中文/日文/韩文？**
A：系统流水备注按创建时客户端语言生成（`Accept-Language`），随 UI 语言展示；历史数据保持创建时语言（快照语义）。

**Q6：合并后源账户的“历史”去哪了？**
A：交易的 source/target 全部重指到目标账户，目标账户余额按账本重算。历史一行不少，只是换了归属。

## 9. 测试覆盖（tests/unit/services/test_account_lifecycle.py）

- UPSERT：身份保持、余额不被重置、不隐式删账户、CLOSED 保持；
- 删除：引用守卫 / 余额守卫 / 空账户可删 / 停用+历史 → 3312 专门提示；
- 合并：自并、币种、性质、目标关闭守卫；历史重指 + 余额重算；
- 停用：keep 冻结快照、transfer 资产转出、writeoff 资产核销、已停用 409；
